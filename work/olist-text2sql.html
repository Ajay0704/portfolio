Fine-Tuning a Small Model to Write SQL

I fine-tuned two small open models with LoRA to turn business questions into SQL on Olist’s database. On a 150-question test locked before training, Qwen3.5-4B went from 52 to 78 correct and Llama 3.2 3B from 18 to 51.7, averaged over 3 training runs. Every run beat its untrained model.

The Business Problem

Managers ask data questions in plain English all day: which sellers ship late, how much do we spend on freight, what share of orders arrive on a weekend? Each one waits in an analyst’s queue for a SQL query. Large hosted models can write that SQL, but every call costs money and sends the question outside the company.

So the question I tested was: can a small, open model that runs on one GPU learn to write correct SQL for one company’s database? I used Olist, a Brazilian e-commerce marketplace that published 99,441 real orders across 9 tables. A manager asks a question, and the model has to write a SQLite query that returns the right answer.

It’s the same Olist data as my e-commerce dashboard, so I already knew where its traps were.

Approach

The exam came first, and it was locked. Before any model ran, I wrote 150 test questions: 139 around the 9 business themes in Olist’s own README, plus the 11 Olist questions from the Spider 2.0 benchmark. Each one targets a real trap in the data, such as one row per item, missing delivery dates or several reviews per order. I fingerprinted the files (SHA-256) and never edited them again.

Scored by results, not by text. An answer counts only if the SQL runs and returns the same result as the reference query (execution accuracy).

Training data written and checked separately. 574 training and 108 validation examples from 118 question families, drafted with Claude. Every query was run against the database and cross-checked by a second, differently written query. Three automatic checks stop any training example from resembling a test question, and no Gemini output was used for training.

LoRA, not a full retrain. Qwen3.5-4B and Llama 3.2 3B Instruct, fine-tuned with LoRA (rank 16) using Unsloth on a Colab L4 GPU: 2 epochs at a learning rate of 1e-4. Only a small adapter is trained (about 120 MB for Qwen), and the checkpoint is chosen on the validation set, never the test.

A fair comparison. Same prompt and schema for every model, deterministic answers (greedy decoding), and the untrained model scored on the same GPU and code. Each model was trained 3 times with different seeds, and gains are tested with McNemar’s exact test on the same 150 questions, with pass rules written before the runs.

One Real Question, Before and After

Test question A09, word for word, with both Qwen answers exactly as the models wrote them.

“How many orders contain items from more than one seller?”

Untrained Qwen3.5-4BWrong: 1,278 rows
SELECT COUNT(*) AS order_count
FROM olist_orders o
JOIN olist_order_items oii ON o.order_id = oii.order_id
GROUP BY o.order_id
HAVING COUNT(DISTINCT oii.seller_id) > 1;
Fine-tuned Qwen3.5-4BCorrect: one number
SELECT COUNT(*) AS multi_seller_orders
FROM (SELECT i.order_id
      FROM olist_order_items i
      GROUP BY i.order_id
      HAVING COUNT(DISTINCT i.seller_id) > 1) AS multi_seller

The untrained model found the right orders but counted items inside each one, so it returned 1,278 rows instead of one total. That’s the “one row per item” trap. The fine-tuned model groups first, then counts the groups.

What the First Attempt Taught Me

Round 1 looked great during training and failed on the test. The training loss fell to 0.0003, meaning the model had memorised its examples instead of learning the skill.

+11 → +28

Round 1 gained only 11 questions, which wasn’t significant (p = 0.13). Round 2, with more varied examples and gentler training, gained 28 (p < 0.0001). Changing the data mattered more than training harder.

One run isn’t enough. The random seed alone moved Llama’s score by 9 questions (48 to 57), so I report all three runs, not the best one.

What It Doesn’t Show

  • A small model closing the gap, not beating a large one. My questions spell out exactly what is wanted, so Gemini nearly maxes the test out.
  • Hard questions are still weak. Qwen reaches 25% on hard questions, and the 11 Spider questions stayed at 0 to 1 correct.
  • One dataset, synthetic questions. The training examples were written with an AI assistant, not collected from real users.

Data: Olist, work-at-olist-data (MIT licence), 99,441 orders, Sep 2016 to Oct 2018. Spider 2.0 questions from the Spider 2.0 benchmark. All scores are from my locked test set. Independent project, not affiliated with Olist.
