Fine-tuning small open models for text-to-SQL on a company database

LoRA fine-tuning of Qwen3.5-4B and Llama 3.2 3B on the Olist e-commerce database, evaluated on a locked 150-question test

1Executive summary

This project tested whether a small open-source language model, fine-tuned on a few hundred examples, can reliably turn business questions into correct SQL for one company's database. Two models were fine-tuned with LoRA and scored on a 150-question test that was locked before any model was run.

Findings

  • Fine-tuning works and is repeatable. Every one of the 6 training runs beat its untrained model, and the gain held across three random seeds.
  • Qwen3.5-4B is the stronger base model. It beat Llama 3.2 3B before training (52 vs 18) and after it, winning all three same-seed comparisons.
  • The fine-tuned model is not ready to run unsupervised. It answers 52% of all questions and 25% of hard ones, against 95% for a large hosted model (Gemini 3.8 Flash). It is suited to drafting SQL that an analyst reviews.
  • Training-data design mattered more than training time. The first attempt memorised its data and gave no clear gain; a more varied dataset with gentler settings gave a clear one.

2Background

Most business questions about an online marketplace (which sellers are late, where freight is expensive, which categories get poor reviews) can be answered from its order database, but only by someone who writes SQL and knows where the data's traps are. A model that writes correct SQL for that specific database would let more people get answers without waiting for an analyst.

Large hosted models already write SQL well, but they send company data to an outside service and are billed per request. A small open model can run on the company's own hardware. The question is whether a small model can be made good enough on one company's schema with a modest amount of training.

3Objectives and non-goals

ObjectivesNon-goals
  • Measure how much LoRA fine-tuning improves a small open model's SQL on one real schema.
  • Compare two open base models under identical conditions.
  • Place the results against a large hosted model as a reference point.
  • Report results that hold up statistically, including run-to-run variation.
  • Beat large hosted models.
  • Build a production service, user interface or chat assistant.
  • Generalise across many databases (one schema only).
  • Tune for speed or serving cost.

4System overview

5Data

  • Source database. Olist's public Brazilian e-commerce dataset: 99,441 orders placed between September 2016 and October 2018, in 9 tables (orders, order items, payments, reviews, customers, sellers, products, category names, geolocation). It is loaded into SQLite with 18 indexes. Table names match the Spider 2.0 benchmark's copy of the same data. [1]
  • Test set (150 questions). 139 questions were written for this project across the 9 business themes listed in Olist's own README, and reviewed in batches. The other 11 are the Olist questions published in the Spider 2.0 benchmark [2], used for testing only.
  • Data traps. Questions deliberately test known pitfalls in the real data, for example that an order has one row per item, that delivery dates are missing for undelivered orders, and that some orders have several reviews.
  • Training set. 574 training and 108 validation examples, generated from 118 question "families" written with Claude (Anthropic). Every query was run against the database and cross-checked by a second, independently written query. Whole families are held out for validation.
  • Leakage controls. Each training question is compared with all 150 test questions: text similarity below 0.75, word overlap below 0.6, and no identical results. No output from the reference model (Gemini) was used for training.

6Evaluation design

Metric

Execution accuracy. An answer is correct only if the generated SQL runs and returns the same result as the reference query. Results are compared on values, not column names; row order counts only when the question asks for an order; numbers are rounded to 2 decimal places. The 11 Spider questions use Spider's own grading rule. Generated SQL runs against a read-only connection, must be a single SELECT, and is stopped after 30 seconds.

Controls

  • The test files were fingerprinted with SHA-256 before any model was run and verified before every scoring run.
  • All models receive the same prompt (instructions plus the database schema) and decode greedily, so answers are deterministic.
  • The untrained baseline for each model was run on the same GPU and code as its fine-tuned version.
  • Checkpoints are chosen on the validation set only. The test set is never used to choose anything.
  • Each model was trained three times (seeds 3407, 42 and 1234), and every run is reported.

Statistical method and decision rules

Two runs on the same 150 questions are compared with McNemar's exact test [4], which uses only the questions where the runs disagree. Single scores carry 95% Wilson intervals [5]. At 150 questions, a paired difference of about ±9 points can arise by chance. Three rules were written down before the repeat runs:

  1. All three seeds are reported for each model, never only the best.
  2. Fine-tuning counts as working for a model only if every seed beats its untrained model with p < 0.05.
  3. Qwen counts as better than Llama only if its mean is higher and it wins every same-seed pair.

7Training

Both models were fine-tuned with LoRA [3], which freezes the original weights and trains small low-rank matrices added to the attention and feed-forward layers. Training used Unsloth on one NVIDIA L4 GPU in bf16 (Google Colab). Loss is computed on the SQL answer only; the prompt is identical to the one used at test time.

Round 1 memorised its training data: training loss fell to 0.0003 and the model began copying the training SQL's alias style, which broke 16 questions it had answered correctly before. Round 2 changed the data and settings following Unsloth's guidance on overfitting [6]; final training loss stayed between about 0.06 and 0.12.

11Risks and limitations

  • Test difficulty. The project questions state exactly what is wanted, so the large reference model answers all 139 of them correctly. The test shows a small model closing the gap with a large one, not beating it.
  • Hard questions. Accuracy on hard questions is 25% (Qwen). The 11 Spider questions, which are less precisely worded, stayed at 0 or 1 correct for every small-model run.
  • Scope. One database and one SQL dialect. Results do not show how the method transfers to another schema.
  • Training data origin. Training examples were written with an AI assistant and validated by execution, not collected from real users, so real questions may be phrased differently.
  • Operational safety. Wrong SQL that runs returns a plausible-looking wrong number. Any use needs read-only access (as in this evaluation), query time limits, and human review of results.
  • Test size. With 150 questions, differences under about 9 points cannot be separated from chance. The main results are well above that level.

12Conclusions and recommendations

  1. LoRA fine-tuning on about 600 checked, schema-specific examples reliably improves a small open model's SQL on that schema: +26 questions for Qwen and +34 for Llama on average, consistent across seeds.
  2. Qwen3.5-4B is the recommended base model among those tested.
  3. The fine-tuned model should be used to draft SQL for an analyst to review, not to answer business users directly.
  4. The next improvement should target query logic on hard questions, through more hard training families and a harder, less precisely worded evaluation set, rather than longer training.

Appendix C · Glossary

LoRALow-Rank Adaptation. Trains small added matrices instead of the whole model, so training fits on one GPU and the result is a small adapter file.
Execution accuracyThe share of questions where the generated SQL returns the same result as the reference query.
SeedThe number that fixes the random choices in training (starting values, data order, dropout). Different seeds give different runs of the same recipe.
Validation setHeld-back training-style examples used to choose the checkpoint, so the test set is never used for any choice.
McNemar's testA paired test for two systems scored on the same items; it uses only the items where they disagree.
Data trapA property of the real data that makes a question easy to answer wrongly, such as missing dates or one row per item.
